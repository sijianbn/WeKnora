WeKnora Fork 自维护策略

上游（Tencent/WeKnora）不一定接受每个 PR，但业务要用。策略：fork 即产品——fork 上维护一条集成分支 bn-main（上游 main + 你的未合并补丁），部署永远从 bn-main 构建；每个功能一个干净的特性分支，与 PR 一一对应，随时可独立提交上游，互不干扰。

核心模型一图流

Tencent/main  ──┬─────────────┬──────────────┬──→  (上游持续前进)
                    │           │           │
特性分支        feat/xxx-3087  feat/yyy    feat/zzz    (= fork 上的 PR 分支)
                    │ merge     │ merge     │
bn-main      ──┴─────────────┴──────────────┴──→  (你的部署源，永远可构建)
分支角色推送目标规则
bn-main集成分支 / 部署源fork（备份 + CI）永不直接开发，只做 merge/rebase
feat/*功能分支 / PR 载体fork（即 PR 源分支）小而独立，只碰必要文件
origin/main上游真相只 fetch，永不 push每次集成的基准
私有内容也走 feat 分支：不打算提上游的内容（如 docs_for_bn/ 私有文档）同样从 origin/main 切独立分支维护（例：feat/docs-for-bn），只是永不提 PR。「bn-main 永不直接开发」对这类内容同样生效——改动一律先落在分支上，再 merge 进 bn-main。

本机远端布局（注意：与常见惯例相反）

远端名指向用途
originhttps://github.com/Tencent/WeKnora.git
（HTTPS + github.com 作用域代理）		上游，只读：fetch 同步用（大流量走代理，实测 ~19 MiB/s）
forkgit@github-sijianbn:sijianbn/WeKnora.git
（SSH 别名，sijianbn 密钥）		你自己的 fork：push 特性分支与 bn-main（小流量 SSH 直连，秒通且免凭据）
网络策略（2026-09-09 实测定型）：直连 github.com:443 会被重置；SSH 22 能通但持续大流量被限速到 ~10 KB/s；HTTPS + 本地代理最快。git 已配置仅对 github.com 生效的代理（不影响 goproxy.cn 等其它 host）：
git config --global http.https://github.com.proxy http://127.0.0.1:7890
代理没开时：先开代理；或临时把 origin 切成 git@github.com:… 用 SSH 慢速拉。双账号靠 ~/.ssh/config 别名主机区分，见「双账号 SSH 密钥」。
新电脑恢复（按下述顺序执行一次）：
# 1) 放好两把 OpenSSH 格式密钥并写好 ~/.ssh/config（见「双账号 SSH 密钥」）
# 2) 克隆 + 挂上游
git clone --config core.autocrlf=false git@github-sijianbn:sijianbn/WeKnora.git WeKnora
cd WeKnora
git remote add origin https://github.com/Tencent/WeKnora.git
git config --global http.https://github.com.proxy http://127.0.0.1:7890   # 开着代理时
git fetch origin
git checkout -b bn-main fork/bn-main        # 从 fork 拉回已有 bn-main（含自己的补丁）
git branch --set-upstream-to=fork/bn-main bn-main
（CRLF 参数的原因见《Docker 编译环境》文档踩坑 #4）

同步上游（每周 / 每次要用上游新功能前）

git checkout bn-main
git fetch origin                          # 拉上游最新
git rebase origin/main                    # bn-main 的补丁整体搬到新 main 上
# 有冲突 → 解决后 git add + git rebase --continue；想放弃 → git rebase --abort
git push -f fork bn-main
为什么用 rebase 而不是 merge：补丁少（个位数）时 rebase 历史最干净——bn-main 永远等价于「最新上游 main + N 个自己的 commit」，一眼能看出自己改了什么。补丁超过十几个或经常冲突时再改用 merge 策略。

新功能开发（产出一个 PR + 一次集成）

# 1. 从最新上游 main 切出特性分支（保证 PR 干净可合并）
git checkout -b feat/描述性名字 origin/main

# 2. 开发 + 自测（编译环境见《Docker 编译环境》文档）
#    sh docs_for_bn/docker-go.sh test ./受影响包/... -count=1

# 3. 提交并推到 fork → GitHub 上开 PR（Tencent/WeKnora）
git add ... && git commit -m "feat(scope): ..."
git push -u fork feat/描述性名字

# 4. 不管上游是否接受，先合入自己的 bn-main 用起来
git checkout bn-main
git merge feat/描述性名字
git push fork bn-main

构建部署（永远从 bn-main）

git checkout bn-main
docker compose build app frontend          # 本地构建自己的镜像
docker compose up -d

不依赖官方 wechatopenai/weknora-* 镜像 tag；上游版本升级 = 同步上游后重新 build。

上游接受了你的某个 PR

  1. 同步上游（rebase 时，Git 会发现你的补丁与上游新 commit 内容相同而自动丢弃——rebase 的去重）
  2. 若没自动去掉（SHA 不同内容相同偶尔发生）：git rebase --onto origin/main <旧基> bn-main 或手动 git rebase -i origin/main drop 掉对应 commit
  3. 对应的 feat/* 分支可以删除：git branch -d feat/xxx && git push fork --delete feat/xxx

上游明确拒绝 / 长期无人理

  • 拒绝：分支保留继续在 bn-main 上活着；如果拒绝理由充分（方案之争），评估是否调整方案重提——调整时开新分支，旧分支留档
  • 长期无人理：每隔几周 rebase 保活一次（见下方「PR 保活」），并在关联 issue 下礼貌顶帖
PR 保活命令
git checkout feat/xxx
git fetch origin
git rebase origin/main
git push -f fork feat/xxx
维护者永远看到「可干净合并」的 PR，这是被接受的重要加分项。

双账号 SSH 密钥（本机实际情况）

现状：本机有两把 GitHub 密钥、两个账号——默认 Host github.com 走 bruceasdqwe.ppk2（bruceasdqwe 账号），fork 所属的 sijianbn 账号走别名主机 github-sijianbn。~/.ssh/config 全文：
Host github.com
  IdentityFile ~/.ssh/bruceasdqwe.ppk2

# sijianbn 账号专用别名：fork（sijianbn/WeKnora）推送走这里
Host github-sijianbn
  HostName github.com
  User git
  IdentityFile ~/.ssh/sijianbn_github.ppk2
  IdentitiesOnly yes
要点：
① push fork 一律用 git@github-sijianbn:sijianbn/WeKnora.git 形式的地址（本仓库的 fork remote 已配置好），SSH 自动选对密钥，不再需要 -c credential.username=sijianbn。
② .ppk 是 PuTTY 私钥格式，OpenSSH（git 所用）读不了；.ppk2 才是转换后的 OpenSSH 格式。转换命令（puttygen 可用 TortoiseGit 自带的）：puttygen key.ppk -O private-openssh-new -o key.ppk2。
③ 验证某把钥匙的身份：ssh -T -i ~/.ssh/xxx git@github.com，看返回「Hi 谁」。
④ 通道实测（2026-09-09）：直连 443 被重置；SSH 22 稳定但限速；HTTPS+代理最快。故 fork 推送走 SSH 别名（小流量、免凭据），origin 大 fetch 走 HTTPS+代理；-c credential.username=sijianbn 保留为 HTTPS 推 fork 的备用手段。

fork 上的免费 CI

GitHub Actions 在自己的 fork 里不需要维护者批准。工作流：推到 fork → fork 的 Actions 页直接跑（若默认禁用，在 fork 的 Actions 标签页点 "I understand my workflows, go ahead and enable them"）。这样可以在提 PR 之前就完成 CI 自验，把「等维护者批准 workflow」的被动等待变成提前验证。

三条实践原则（决定这套流程痛不痛苦）

  1. PR 小而独立：只碰必要文件、功能之间零依赖。上游接受一个 → bn-main 删一个补丁，无连锁反应。反例：一个 500 行大杂烩 PR，上游改一行就全线冲突。
  2. bn-main 永不直接开发：所有代码先进 feat/* 再 merge 进来。否则补丁边界糊掉，将来无法「单独摘出来给上游」。
  3. 部署前必从 bn-main 干净构建：git status 有未提交改动时不要 build 镜像——镜像是可复现的交付物，别让它夹带工作区状态。
