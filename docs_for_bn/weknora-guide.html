WeKnora 使用指南与功能全景

腾讯开源的企业级知识管理框架：RAG 快速问答 · ReAct Agent 智能推理 · 自动 Wiki 生成与知识图谱 · 会话级沙箱技能 · 多端发布集成。

本页面基于仓库 README_CN.md、website-docs/、docs/、docker-compose.yml、.env.example、mcp-server/ 等内容整理，纯离线可读。

Go 后端 + Vue 前端Python docreader 解析MCP Server（29 工具）MIT License支持私有化部署

1. 项目与架构总览

WeKnora（维娜拉）围绕三大核心能力构建：RAG 快速问答（日常知识查询）、ReAct Agent 智能推理（自主编排知识检索、MCP 工具、技能沙箱与网络搜索）、Wiki 模式（Agent 从原始文档自治生成相互链接的 Markdown Wiki 与可视化知识图谱，支持人工编辑、版本历史与一键回滚）。全流程模块化：模型、向量库、对象存储、搜索后端均可替换，数据完全自主可控。

1.1 系统架构图

图 1 · WeKnora 系统架构：客户端层 → Go 后端核心 → 解析 / 沙箱 / 模型 / 搜索 → 数据存储层

典型 RAG 数据流：上传文档 → docreader 解析（OCR / VLM / ASR 可选）→ 分块（自适应三层 / 父子分块）→ Embedding 向量化 → 写入向量库；问答 → 问题向量化 → BM25 稀疏 + Dense 稠密 + GraphRAG 图谱混合召回 → Rerank 重排 → LLM 生成带引用回答（SSE 流式输出）。

2. 快速启动指南

2.1 环境准备

  • 必需：Docker & Docker Compose、Git。
  • 模型：至少一个对话模型（LLM）+ 一个向量模型（Embedding）。本地 Ollama 需先运行 ollama serve；容器内访问宿主机 Ollama 地址为 http://host.docker.internal:11434（高频踩坑 填 localhost:11434 连不上）。
  • 硬件无硬性门槛；使用本地模型时按模型规模准备 GPU / 内存。

2.2 Docker Compose 启动

# 1) 克隆并进入项目
git clone https://github.com/Tencent/WeKnora.git
cd WeKnora

# 2) 生成环境配置（按需编辑 .env，文件内有逐项中文注释，标 ⚠️ 的为必填）
cp .env.example .env

# 3) 拉取镜像并启动核心服务
docker compose pull
docker compose up -d

# 4) 验证后端存活
curl http://localhost:8080/health   # 返回 {"status":"ok"}

# 5) 浏览器访问 Web UI
#    http://localhost        → 前端
#    http://localhost:8080   → 后端 API（Swagger 在 GIN_MODE=debug 时开放）
#    http://localhost:3000   → Langfuse（--profile langfuse 启动后）
⚠️ 实战教训：nginx 在启动时一次性解析 app 的容器 IP 并固定。此后只要重建 / 重启了 app（改 .env、升级、引擎重启后容器重建等），必须连带重启 frontend，否则静态页面能打开但所有 /api 请求 502。安全做法：docker compose up -d --force-recreate app frontend。完整案例见 第 16 章。

3. 首次使用与模型配置

3.1 注册、登录与工作空间

  • 首次访问 http://localhost 落到登录页，注册是同页页签（仅注册模式为 self_serve 时显示，前端读 /auth/config 决定）。系统没有内置默认账号。
  • 用户名 2–50 字符；界面注册要求密码 8–32 位且含字母和数字。注册后自动获得一个专属工作空间，你是该空间的 Owner。
  • 空间 Owner ≠ 系统管理员：Owner 管本空间的成员/模型/知识库；系统管理员管整个部署（全局设置、任务队列、平台 API Key、跨空间审计、密码重置），首个系统管理员需用 WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL 显式指定。
  • 团队部署建议注册第一个账号后关闭公开注册（DISABLE_REGISTRATION=true 或「设置→系统」改 auth.registration_mode），之后用邀请链接加人。
  • 桌面版 / Lite 版免注册，启动即创建本地账号。

3.2 配置模型（LLM / Embedding / Rerank / VLM / ASR）

WeKnora 的模型配置是按知识库走的：新建知识库后弹出初始化向导，逐步配置。也可在「设置 → 模型」中管理空间级/内置模型（YAML 声明式内置模型配置，多空间共享）。

模型类型是否必需作用与说明
对话模型 LLM必需生成回答；支持 OpenAI / Azure OpenAI / Claude / DeepSeek / Qwen / 智谱 / 混元 / 豆包 / Gemini / MiniMax / NVIDIA / Novita / SiliconFlow / OpenRouter / Requesty / LiteLLM / Ollama 等 20+ 厂商；可按模型开启思考模式与 Prompt Cache
向量模型 Embedding必需文档向量化；Ollama / BGE / GTE / 智谱 / OpenAI 兼容接口。建库后不要更换，换了需重建索引；默认 1024 维（pgvector HNSW）
重排 Rerank可选混合召回后重排，提升精度；支持火山引擎 Rerank（自动分批）、腾讯云 LKEAP 等
图片理解 VLM可选图片内容描述，支撑多模态问答与自动打标
语音转写 ASR可选音频文档转文字
图谱抽取模型可选实体 / 关系抽取（需 Neo4j），向导内可试抽取预览
问题预生成可选为分块预生成问题，改善召回与推荐问题
配置项都可用向导中的「测试 / check」按钮先验证连通性（对应 /api/v1/initialization/remote/check、/embedding/test、/rerank/check、/asr/check、/multimodal/test 等端点），再保存。

4. 知识库：创建、上传与解析

4.1 完整使用流程步骤图

启动服务docker compose up -d，访问 localhost
注册登录获得专属空间，成为 Owner
创建知识库选类型：document / faq
配置模型初始化向导选 LLM + Embedding，测试连通
上传文档拖拽文件 / URL 导入 / 文件夹导入，确认解析选项
等待解析pending → processing → finalizing → completed
检索问答选择知识库提问，带引用流式回答
扩展发布Agent / Wiki / IM / 嵌入 Widget / API / MCP

4.2 上传、解析与分块

  • 导入方式：拖拽上传（批量）、网页 URL 导入、文件夹导入（保留树形目录结构）、本地 HTML 上传、在线录入；Chrome 插件可直接采集网页。
  • 支持格式：PDF / Word / Txt / Markdown / HTML / EPUB / MHTML / 图片 / CSV / Excel / PPT / JSON / XMind / 音频（ASR）。Office 文档可由 anydoc 在 Go 进程内解析（构建开关 WITH_ANYDOC）。
  • 解析引擎：内置 docreader、OpenDataLoader、PaddleOCR-VL 等，可在上传确认对话框或 process_config 中按批次覆盖；支持文档重新解析（reparse）与批量重新解析。
  • 分块：自适应三层分块 / 父子分块；chunkSize 100–10000、chunkOverlap、分隔符均可配；解析追踪时间线逐阶段展示进度，可中止。
  • 分块编辑与版本历史：界面直接编辑检索分块，逐版本 diff 与回滚，编辑后自动重建索引；支持文档自定义元数据与多标签。
  • 自动打标签：解析完成后从知识库已有标签中选择匹配项增量关联（不新建、不覆盖人工标签）。

4.3 数据源自动同步

支持从外部平台自动同步知识：飞书知识库 / 飞书云盘 / Lark / GitLab / 腾讯 IMA / Notion / 语雀 / RSS 订阅，支持增量与全量同步；凭据 AES-256-GCM 加密存储。在「设置 → 数据源」中配置连接。

5. 检索与对话问答

检索策略（多路混合）

检索方式说明
BM25 稀疏召回关键词级倒排检索，适合精确词匹配
Dense 稠密召回Embedding 向量相似度检索，pgvector HNSW（1024 维）加速；支持跨向量库扇出
GraphRAG 图谱增强查询 Neo4j 实体关系网络，扩展答案的关联广度（需开启知识图谱）
父子分块小块精准命中、大块上下文回填
Rerank 重排对召回结果精排，附带段落清洗
知识搜索 APIPOST /knowledge-search 仅检索不生成，返回结构化 JSON
端到端评估检索+生成全链路可视化，评估召回命中率、BLEU / ROUGE 等指标

对话能力

  • 快速问答：RAG 流水线（检索 → 生成 → 带出处），SSE 流式 Markdown 渲染，引用浮层 / 引用抽屉区分网络与知识库来源。
  • 智能推理（ReAct Agent）：自主决定检索几轮、是否联网、调用哪些工具；内置 agent_id builtin-smart-reasoning。
  • 对话策略：在线编辑 Prompt、调节检索阈值、多轮上下文感知、按 Agent 引用输出开关、思考模式。
  • 推荐问题与追问：基于知识库内容自动生成推荐问题与答后追问。
  • 临时附件：会话内临时上传图片 / 文档，异步解析后一次性使用（合并限额）。
  • 长期记忆：跨会话记忆 profile / preference / fact / task / interest，自动抽取需用户确认，Agent 可调用 search_memory。
  • 会话管理：按来源（Web / IM / 嵌入）筛选分组、搜索、置顶、批量管理、Markdown 导出；上下文压缩。

6. Wiki 模式与知识图谱

Wiki 模式：Agent 自动生成知识库

Wiki 模式让 Agent 从原始文档自治生成结构化、相互链接的 Markdown Wiki 页面，并构建可视化知识图谱。支持：Wiki 浏览器 + 文件夹层级导航、浏览器内人工编辑、页面版本历史（快照 + 行级 diff + 一键回滚）、对话引用抽屉展示 Wiki 工具结果。大库场景由独立任务队列 + 死信队列支撑（可入库万级文档）。

知识图谱（GraphRAG）启用步骤
  1. 编辑 .env：NEO4J_ENABLE=true、NEO4J_URI=bolt://neo4j:7687、NEO4J_USERNAME=neo4j、NEO4J_PASSWORD=...
  2. 启动 Neo4j：docker compose --profile neo4j up -d
  3. 在知识库设置（初始化向导「实体关系抽取」）中启用，并按提示配置抽取模型；可用 /initialization/extract/text-relation 试抽取预览效果。
  4. 上传文档后系统自动提取实体与关系生成图谱；对话时自动查询图谱辅助检索。
  5. 查看图谱：http://localhost:7474 执行 match (n) return (n)，或在 Wiki 图谱可视化页面查看。

7. Agent、技能与沙箱

  • 自定义 Agent：「智能体」页创建，可挂知识库、MCP 工具、网络搜索、技能；按 Agent 配置 LLM 超时与引用开关。
  • 技能目录：空间级技能目录，从 ClawHub / SkillHub / git / zip 安装技能；支持按沙箱快照、实时进度、文件浏览/编辑、个人与空间环境变量。
  • 会话级沙箱：Docker / E2B / Cube 三种后端（v0.8 起移除 Local 宿主机进程后端）。一个会话一个长驻容器，脚本、shell_exec、附件暂存、产物收集都在同一容器内。Docker 后端默认关闭（docker.sock 等同宿主机 root），系统管理员在「设置 → 系统 → 网络安全」显式开启或设 WEKNORA_SANDBOX_DOCKER_ENABLED=true；按空间配置 CPU / 内存 / 网络 / TTL 策略。
  • @Skill / @MCP 提及：在对话中 @ 引用以按轮次范围化 Agent 运行时；会话内支持 MCP OAuth 授权。
  • 工具生态：内置工具 + MCP 工具（含 OAuth2 远程服务）+ 网络搜索（11 种后端）+ final_answer 工具 + 并行工具调用；MCP 返回图片可由 VLM 自动描述。

8. API 调用与认证

统一前缀 /api/v1，约 360 个端点；完整契约见 docs/swagger.json（GIN_MODE=debug 时可访问 Swagger UI）与 website-docs/04-api/。

三种认证方式

方式请求头适用
JWTAuthorization: Bearer <token>浏览器 / 交互式调用，登录接口签发
API KeyX-API-Key: <key>服务端集成；细粒度能力授权（retrieve / chat / ingest / manage_kbs 等）+ 按 KB 限制 + 节流 last_used 追踪；另有平台级 API Key 用于控制面自动化
指定空间X-Tenant-ID: <id>多空间用户切换当前工作空间

8.1 常用 curl 示例（可直接复制运行）

BASE=http://localhost:8080/api/v1

# 1) 注册首个账号
curl -s -X POST $BASE/auth/register -H "Content-Type: application/json" \
  -d '{"username":"admin","email":"admin@example.com","password":"pass123456"}'

# 2) 登录取 JWT
TOKEN=$(curl -s -X POST $BASE/auth/login -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"pass123456"}' | jq -r '.token')
AUTH="Authorization: Bearer $TOKEN"

# 3) 创建知识库
KB_ID=$(curl -s -X POST $BASE/knowledge-bases -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"name":"我的知识库","description":"demo","type":"document"}' | jq -r '.data.id')

# 4) 初始化模型与分块配置（本地 Ollama 示例）
curl -s -X POST $BASE/initialization/initialize/$KB_ID -H "$AUTH" -H "Content-Type: application/json" -d '{
  "llm":       {"source":"local","modelName":"qwen3:8b"},
  "embedding": {"source":"local","modelName":"bge-m3","dimension":1024},
  "rerank":    {"enabled":false},
  "multimodal":{"enabled":false},
  "documentSplitting":{"chunkSize":512,"chunkOverlap":50,"separators":["\n\n","\n","。"]},
  "nodeExtract":{"enabled":false},
  "questionGeneration":{"enabled":false}}'

# 5) 上传文档（multipart，字段名 file），随后轮询 GET /knowledge-bases/$KB_ID/knowledge 直到 parse_status=completed
curl -s -X POST $BASE/knowledge-bases/$KB_ID/knowledge/file -H "$AUTH" -F "file=@./demo.pdf"

# 6) 创建会话
SESSION_ID=$(curl -s -X POST $BASE/sessions -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"title":"第一次对话"}' | jq -r '.data.id')

# 7) 知识问答（SSE 流式）
curl -N -X POST $BASE/knowledge-chat/$SESSION_ID -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"query":"这份文档讲了什么？","knowledge_base_ids":["'$KB_ID'"]}'

# 7b) Agent 对话（同为 SSE）
curl -N -X POST $BASE/agent-chat/$SESSION_ID -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"query":"总结文档要点","agent_enabled":true,"agent_id":"builtin-smart-reasoning","knowledge_base_ids":["'$KB_ID'"]}'

# 8) 仅检索不生成
curl -s -X POST $BASE/knowledge-search -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"query":"关键字","knowledge_base_ids":["'$KB_ID'"]}'

# 9) 创建 API Key（服务端集成推荐）
curl -s -X POST $BASE/tenants/$TENANT_ID/api-keys -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"name":"ci-bot","full_access":true}'
# 之后所有请求改用：curl -s $BASE/knowledge-bases -H "X-API-Key: <key>"
问答请求体还支持 knowledge_ids（限定单文档）、web_search_enabled、summary_model_id、mcp_service_ids、skill_names、images / attachment_uploads（多模态附件）等字段；?resource_urls=public 可让响应直接返回限时文件直链。

9. MCP Server

WeKnora 提供两个方向的 MCP 能力：

  • 作为 MCP 客户端：在「设置 → MCP 服务」集中管理外部 MCP 服务（SSE / HTTP Streamable / Stdio 三种传输），支持连接测试（列出工具清单与 schema）、启停、超时重试、API Key/Bearer 鉴权、OAuth2 与会话内 OAuth 授权；Agent 推理时可调用这些工具。
  • 作为 MCP Server 供外部调用：官方 PyPI 包 tencent-weknora-mcp，共 29 个工具，支持 stdio / SSE / HTTP 三种传输，端口默认 8082；v0.7.2 起新增 create_knowledge_from_text、list_shared_knowledge_bases，含人机审批与多传输。另支持内置 MCP 服务（BUILTIN_MCP_SERVICES.md）。
MCP Server 安装与客户端配置（Claude Desktop / Cursor）
# 安装（推荐 uv 运行）
pip install tencent-weknora-mcp
# 或：uvx --from tencent-weknora-mcp weknora-mcp-server
// Claude Desktop / Cursor 的 mcpServers 配置
{
  "mcpServers": {
    "weknora": {
      "command": "uv",
      "args": ["--directory", "/path/WeKnora/mcp-server", "run", "run_server.py"],
      "env": {
        "WEKNORA_API_KEY": "your_api_key_here",
        "WEKNORA_BASE_URL": "http://localhost:8080/api/v1"
      }
    }
  }
}

需要先在 WeKnora「空间设置」中创建一个具备相应能力的 API Key。更多示例见仓库 mcp-server/MCP_CONFIG.md 与 mcp-server/EXAMPLES.md。

15. 常见问题与排错

Ollama 连不上？

后端在容器内，localhost:11434 指向容器自身。应填 http://host.docker.internal:11434，并确保宿主机已运行 ollama serve。初始化向导提供 Ollama 检测 / 模型列表 / 异步下载端点。

Embedding 模型能中途更换吗？

不建议。向量维度与语义空间绑定，建库后更换需重建全部索引；初始化向导在库中已有文件时会限制修改 embedding。

IM 里图片不显示？

IM 平台需要公网可达的 http URL。二选一：(A) 存储后端本身公网可达；(B) 设置 APP_EXTERNAL_URL 让 resource:// 引用改写为 <APP_EXTERNAL_URL>/r/<token>（nginx 需代理 /r/）。本地开发用 ngrok / cloudflared / frp。

沙箱不生效 / 找不到 Docker 选项？

v0.8 起 Docker 沙箱默认关闭（docker.sock 等同宿主机 root）。系统管理员在「设置 → 系统设置 → 网络安全」开启，或设 WEKNORA_SANDBOX_DOCKER_ENABLED=true 作为未落库时的回退。Local 宿主机进程后端已移除。

升级后 Web UI 版本不一致？

仅执行 docker compose up -d 会复用本地缓存镜像。升级时先在 .env 设置 WEKNORA_VERSION，再执行 docker compose pull && docker compose up -d。

忘记系统管理员 / 需要提权？

新部署没有系统管理员。先正常注册账号，然后给 app 设 WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL=<邮箱> 并重启（仅当部署中没有任何系统管理员时生效）。之后在界面管理；管理员密码重置会吊销该用户会话。

如何排查 LLM 上下文问题？

设置 LLM_DEBUG_LOG=true，每次大模型调用的完整请求 / 响应写入 LOG_PATH 同目录的 llm_debug.log；结合 Langfuse 追踪查看 ReAct 循环与 Token 消耗。更多排查见 docs/QA.md。

16. 实战运维经验（部署实录 · 2026-09-06）

本章是本机实际部署 WeKnora（默认栈 + MinIO + Neo4j + Langfuse 三 profile）当天踩坑与恢复的完整复盘，所有命令均在本机验证有效。核心结论先给：

三条铁律：① 改过 app 相关配置重启时，把 frontend 一起重启（nginx 记死旧 IP）；② Docker 引擎异常后，先跑一遍 docker compose --profile minio --profile neo4j --profile langfuse up -d 补齐没起来的容器，再考虑重启 Docker Desktop；③ 排障先分层——页面 200 不代表 API 通，API 通不代表容器健康。

16.1 快速恢复流程

遇到「打不开 / 报错」时按此流程走，多数 10 分钟内恢复：

先测三个端点页面 :80 · 匿名 API /api/v1/auth/config · Langfuse :3000，判断断在哪一层
补容器docker compose --profile minio --profile neo4j --profile langfuse up -d，up 会自动补起退出/缺失的容器
查容器真相docker ps -a（必须带 -a，Exited 容器默认不显示）+ docker logs WeKnora-app --tail 50
还不行就重启引擎杀掉 Docker Desktop 全部进程重启（见 16.2 案例 1），容器因 restart: unless-stopped 会自动回来
引擎起来后再补一遍 up引擎崩溃常伴随个别容器 Exited，重启完引擎务必再执行一次第 2 步
端到端验证登录页 200 + 匿名 API 200 + 受保护接口 401（未登录的 401 是好现象，说明链路通）

16.2 三次典型故障案例

案例 1 · Docker Desktop 引擎僵死（当天发生 2 次）

症状（按出现顺序）：

  • docker compose pull 个别镜像报 502 Bad Gateway for API route；
  • 随后 docker ps / docker exec 直接挂起无输出（最典型的信号）；
  • docker info 报 Docker Desktop is unable to start 或 npipe 找不到；
  • 重启恢复过程中 docker info / docker ps 返回 500 Internal Server Error——这是引擎初始化中的暂态，继续等即可，不要反复杀进程。

恢复操作（PowerShell，管理员不需要）：

# 1) 强杀全部 Docker Desktop 进程（UI + 后端）
Get-Process 'Docker Desktop','com.docker.backend','com.docker.build' -ErrorAction SilentlyContinue | Stop-Process -Force
Start-Sleep 8
# 2) 重新拉起
Start-Process 'C:\Program Files\Docker\Docker\Docker Desktop.exe'
# 3) 轮询等待引擎就绪（实测 4~5 分钟，期间 500 是暂态）
docker info --format '{{.ServerVersion}}'   # 能打印版本号即就绪

经验：当天两次恢复时引擎顺带从 29.4.0 自动升级到 29.7.2，反复僵死与此高度相关。容器带 restart: unless-stopped，引擎恢复后会自动回来——但个别容器可能 Exited 起不来（见案例 3），所以要补一遍 up -d。

案例 2 · 页面能打开但所有 /api 502（frontend nginx 记死旧 IP）

症状：浏览器打开 http://localhost/login 是正常登录页（静态文件 200），但点登录无响应；F12 或 curl 看 /api/v1/auth/config 返回 502，nginx 错误页「Sorry, the page you are looking is currently unavailable」。frontend 日志里刷 connect() failed (111: Connection refused) ... upstream: "http://172.21.0.4:8080"——注意这是一个写死的 IP。

根因：frontend 镜像里的 nginx 在启动时把上游主机名 app 解析成 IP 并固定进配置，之后不再重新解析。app 容器一旦被重建（改 .env、升级、引擎重启后重建），就会拿到新 IP，而 frontend 若没跟着重启，nginx 仍指向旧 IP。

修复：docker compose restart frontend（30 秒生效）。预防：以后凡重启 app，连带 frontend：

docker compose up -d --force-recreate app frontend   # 一起重建， nginx 重新解析
# 或改完配置后：
docker compose restart app && docker compose restart frontend

辨别要点：「页面 200 + API 502」几乎必然是这一条，而不是 app 挂了（app 挂了 nginx 会报 upstream not found 的不同错误，且 app 会整容器重启）。

案例 3 · MinIO 容器退出 → app panic 重启循环（故障传导链）

引擎重启后如果只看 docker ps（不带 -a），一切「看起来正常」；实际上 WeKnora-minio 是 Exited (255)，随后引发连锁反应：

图 3 · 引擎崩溃后的故障传导链：一个「不起眼」的 MinIO 退出让整个栈瘫痪

根因：app 在 DI 构建阶段就会连 MinIO 做 bucket 检查（bucket 不存在会自动创建），连不上直接 panic 退出；容器带 restart: unless-stopped 就变成无限重启循环；frontend 的 depends_on: service_healthy 永远等不到 app 健康，停在 Created 状态——于是用户看到的是 nginx 错误页而非 502（frontend 根本没启动）。

修复（一条命令补齐全部）：

docker compose --profile minio --profile neo4j --profile langfuse up -d
# MinIO 起来后，app 在重启循环的下一次尝试即连上并转 healthy，frontend 随之启动
docker compose --profile minio --profile neo4j --profile langfuse ps   # 确认 11 个容器全 Up

16.3 分层排障命令速查

# ---- L1 端点层：判断断在哪一层（页面 200 ≠ API 通）----
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/                        # 前端静态页，期望 200
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/api/v1/auth/config      # 匿名 API，期望 200；502=nginx→app 断（案例2）
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/api/v1/auth/config # 直连 app；通=问题在 nginx，不通=app 本身
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/api/public/health   # Langfuse

# ---- L2 容器层：必须带 -a 才能看到 Exited（案例3 的关键）----
docker compose --profile minio --profile neo4j --profile langfuse ps -a
docker logs WeKnora-app --tail 50          # 找 panic / bootstrap / upstream 关键词
docker logs WeKnora-frontend 2>&1 | grep -E "error|upstream" | tail   # 看 upstream 是不是写死旧 IP

# ---- L3 数据层：直接查库验证（免登录）----
docker exec WeKnora-postgres psql -U postgres -d WeKnora -t -A \
  -c "SELECT email, is_system_admin FROM users ORDER BY created_at;"
docker exec WeKnora-app printenv WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL   # 确认容器真拿到了 .env 新变量

# ---- L4 引擎层：CLI 挂起 / 502 / unable to start → 按案例 1 重启 Docker Desktop ----
docker info --format '{{.ServerVersion}}'   # 挂起或报错=引擎层问题
Git Bash 小坑：在 Git Bash 里 docker run ... --entrypoint /bin/sh 会被 MSYS 路径转换改写成 C:/Program Files/Git/usr/bin/sh 而报错，命令前加 MSYS_NO_PATHCONV=1 即可。

16.4 Langfuse 自建初始化（免手动注册）

compose 的 langfuse-web 支持 LANGFUSE_INIT_* 系列变量，首次启动时自动创建组织、项目、管理员账号，并把自定义 API Key 直接种进项目——省去「浏览器注册 → 手动生成 Key → 回填 .env → 重启 app」四步。本部署实测要点：

变量说明
LANGFUSE_INIT_ORG_ID / LANGFUSE_INIT_PROJECT_ID必填 只填 ORG_NAME 而缺 ORG_ID 时，全部 INIT 变量被静默忽略（日志有 warn，栈照常启动，最易漏）。ID 用小写字母数字连字符，如 weknora-org
LANGFUSE_INIT_PROJECT_PUBLIC_KEY / _SECRET_KEY自拟 pk-lf- / sk-lf- + 32 位 hex。预先生成写入 .env，同一对 Key 同时给 app 的 LANGFUSE_PUBLIC_KEY/SECRET_KEY，一次启动全打通
LANGFUSE_INIT_USER_EMAIL / _PASSWORD管理员账号，仅首启生效（已有数据则跳过）
LANGFUSE_SALT / ENCRYPTION_KEY / NEXTAUTH_SECRETcompose 有开发默认值，生产务必用 openssl rand 生成真随机值
# 修改 INIT 相关变量后需重建两个容器：
docker compose --profile langfuse up -d --force-recreate langfuse-web langfuse-worker
# 验证种入的 Key 可用（200 即成功）：
curl -s -o /dev/null -w "%{http_code}\n" -u "pk-lf-xxxx:sk-lf-xxxx" http://localhost:3000/api/public/projects

注意：app 端要同时设 LANGFUSE_ENABLED=true 与 LANGFUSE_HOST=http://langfuse-web:3000，app 启动日志出现 [Langfuse] enabled host=... 即接入成功。

16.5 系统管理员引导（bootstrap）

机制（源码 cmd/server/bootstrap.go）：app 每次启动时读取 WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL，把该邮箱用户提升为系统管理员。三条硬约束：

  • 账号必须已注册：不会自动创建用户，先在页面正常注册，再配变量重启 app；
  • 仅当系统中没有任何系统管理员时生效：一旦存在系统管理员，此变量不再赋权（防止 UI 撤销被重启悄悄还原），幂等且只提权不降权；
  • 只在启动时执行：运行中改 .env 无效，必须重建 app 容器，并连带重启 frontend（铁律①）。
# .env 配置
WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL=sijianbn@hotmail.com

# 重建并验证（两处日志/数据任一即可确认）
docker compose up -d --force-recreate app frontend
docker logs WeKnora-app 2>&1 | grep -i bootstrap
# 期望: [bootstrap] promoted user <uuid> (sijianbn@hotmail.com) to system admin ...
docker exec WeKnora-postgres psql -U postgres -d WeKnora -t -A \
  -c "SELECT email, is_system_admin FROM users;"   # is_system_admin=t 即生效

后续提权 / 撤销走界面「系统管理员管理页」即可，不必再依赖该变量；保留变量无害（无系统管理员时才会兜底生效）。
